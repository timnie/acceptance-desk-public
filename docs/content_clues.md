# 已有内容判断线索：整理与核对

脚本：`experiments/content_clues.py`。

文风细分表、裁决理由和准备者的对齐审查里，标注者常顺带写到事实、归因、范围或论断强度的变化。这些是人已经写下的判断，补内容标注前应当先复用；但要逐条标明出处和确定程度，不能升级成金标准。

## 清单格式

整理者在仓库外手写一个 JSON：

```json
{"clues": [
  {"id": "k01", "unit": "u001",
   "source": {"kind": "annotator", "who": "B", "field": "note"},
   "quote": "（标注者原话中的一段，逐字摘录）",
   "topic": "归因", "status": "pending", "note": "A 未涉及"}
]}
```

- `source.kind`：`annotator`（标注表某单元格，给 `who` 与 `field`）、`adjudication`（裁决理由）、`preparer`（准备者文件，给 `file`）。
- `status`：
  - `stated`：原话明确写出的判断。只对所指的那一处成立，不代表整个单元无风险。
  - `pending`：原话只说需要核实、复核、可作审查线索，或“涉及内容变化”而未定性。
  - `conflict`：两人对同一点说法相反。
- 没有任何线索的单元是“未涉及”。没写不等于检查过；文风判断为 `no` / `not_present` 也不等于内容无风险。文风裁决只裁文风，不覆盖备注里的内容疑问。
- 状态由整理者按措辞保守标注，写明是整理结果而不是人工判断。

## 核对

```bash
uv run --locked python experiments/content_clues.py 清单.json --a A_判断.csv A_子类.csv --b B_判断.csv B_子类.csv --adjudication 裁决记录.json --preparer 作者裁决对照.md 对齐审查.md --units units_final.json --sample A_判断.csv --report 审计报告.json --render 线索清单.md
```

- 每条原话必须能在所写来源的单元格（或准备者文件）里逐字找到，编号唯一，单元在分区里，状态合法；有一条不过就不输出。
- 覆盖分两层报告：样本单元、完整分区，另列样本外有线索的单元（定向材料）。样本里的比例不外推到全文。
- `--render` 写一份新的可读清单：按单元列原改文和每条线索，最后列出样本内未涉及的单元。来源文件只读，输出只写新文件。

## 作者回答

问题清单回填后，整理者另写一个回答清单 JSON，逐条说明哪段作者原话回应了哪几条线索：

```json
{"resolutions": [
  {"id": "r01", "unit": "u001", "clues": ["k03", "k04"], "quote": "（作者原话中的一段，逐字摘录）",
   "needs_review": "是", "outcome": "resolved", "note": "……"}
]}
```

- `outcome`：
  - `resolved`：原话直接回答了这条线索指出的点；
  - `partly_resolved`：只回答了其中一部分；
  - `other_reason`：作者给了需要看的理由，但不是这条线索指出的那一点（例如只说语体），不转为内容风险；
  - `needs_clarification`：回答与线索方向对不上，要作者解释，不擅自改写方向；
  - `author_undecided`：作者明确写了待定，不替作者补结论。
- 核对：回填文件除“结论”“是否需要作者看”两栏外必须与问题清单模板逐行相同；原话必须在该单元的回填段落里逐字找到；`needs_review` 必须与该单元那一栏逐字相同；只能指向原本待核实、且属于该单元的线索。
- 一个单元可以有多条线索。没被任何回答指到的待核实线索仍记“没有回答”；一段笼统回答不会自动算作解决了该单元的全部线索。
- 作者补答是单人对事实与原意的回答，不是两人独立标注，不计算新的 κ。
- 补充回答（`--supplement`，每个单元一行，如“1. u001：……”）：条目写 `"source": "supplement"`，原话必须在该单元那一行里；补充回答没有“是否需要作者看”一栏，`needs_review` 写 `null`，不推断。后来的回答用 `"supersedes": ["r05"]` 指明取代哪一条，被取代的记录保留并在清单里标出，只是不再参与最终状态。

```bash
uv run --locked python experiments/content_clues.py 清单.json ...（同上）... --resolutions 回答清单.json --answers 回填问题清单.md --template 问题清单.md --render 线索与回答.md
```

## 2026-11-13 在 p01 DeepSeek 末轮稿上的结果

29 条线索，全部逐字可查：明确判断 13、待核实 16、两人说法相反 0。30 个样本单元里 15 个有线索（10 个含待核实）、15 个未涉及；98 个单元里 17 个有线索。现有线索都是“某一处改动”层面的判断，没有任何单元有两人完整的单元级内容标签。清单、可读版和只含 11 个单元的最小问题清单都在仓库外。

作者回答（2026-11-13，论文作者回填 11 题）：16 条待核实线索中，已回答 7、部分回答 2、给了别的理由 2、需澄清 2、作者待定 1、没有回答 2。样本内含待核实线索的 10 个单元里，全部线索都已回答的 4 个；完整分区 11 个单元里 5 个。回答记录、带回答的清单和少量澄清问题都在仓库外。

补充回答（2026-11-13，Tim 转达的六项补充结论）：16 条待核实线索中已回答 10、给了别的理由（文风反馈）5、没有回答 1。样本内 10 个单元中 7 个全部回答，完整分区 11 个中 8 个。

## 复用已有五分类标签

`--labels 已填标注表.csv [--conflicts 冲突.csv]`（需同时给作者回答）：标注表编号必须正好是样本单元、标签是五个代码之一。只列两种机械冲突：作者确认有内容问题而标签是 `no_risk`；作者写“需要看：是”而标注者填了不需要看。类别不同（如作者说“过强”、标签是语义篡改）都属有风险，不算冲突；作者只给文风理由时也不算。方向相反（作者说变弱、标签是论证变强）这类需要人读的冲突，在核对报告里另行列出。

p01 DeepSeek（2026-11-13）：复用 11-11 探索五分类 B 表 30/30（单人标签），机械冲突 0；人工读出方向冲突 1 处，留作未知。按 `label != no_risk` 推出二分类后对照词表 0.2：B 判有风险的 12 个单元提示 9 个，判无风险的 18 个提示 5 个。案例诊断，不是召回率。
